# 探索時間の内訳

2026-11-07、元Mirai（低盤面の最適化は両方OFF）のrelease版を測定しました。

## 配置生成が占めるCPU時間

`movegen::generate` だけを区間計測しました。Mirai内部の探索・一時メモリ確保/破棄を含み、生成結果へのlock・手の報酬評価・グラフ登録・静的盤面評価は含みません。同じ種類の配置を展開内で再利用する場合、再生成として数えません。

| 初期盤面 | 1ワーカー | 4ワーカー |
| --- | ---: | ---: |
| 空 | 31.7%（31.4〜32.0%） | 29.2%（28.5〜29.2%） |
| お邪魔4行 | 32.4%（31.9〜32.6%） | 29.8%（29.6〜30.0%） |

分子は生成処理のスレッドCPU時間の合計、分母は探索全体の全スレッドを含むプロセスCPU時間です。macOSのuser+kernel CPU clockを使い、OSによる待機時間を除外しています。従って4ワーカーの値もCPU処理量の割合であり、3秒の実時間に対する割合ではありません。

## 工程別の実時間

ここでは並列工程の開始から完了待ちまでを一つの区間として測ります。空盤面の3回の中央値です。「展開」に配置生成が含まれるので、上のCPU割合と足してはいけません。

| 工程 | 1ワーカー | 4ワーカー |
| --- | ---: | ---: |
| 葉の選択・選択葉の重複除去 | 2.7% | 2.8% |
| 展開（配置生成＋lock・着手報酬など） | 35.5% | 17.2% |
| ノード・辺の登録、同一盤面の照合 | 28.6% | 53.7% |
| 新規盤面の静的評価 | 27.2% | 14.8% |
| 逆伝播・候補の再整列 | 6.1% | 11.4% |

4ワーカーでは登録が実時間の約52〜54%を占めます。ここは逐次処理なので、並列化されている配置生成だけを高速化しても全体の効果が限られます。4ワーカー時のプロセスCPU消費は、実時間約3秒に対し約5.8CPU秒、平均約1.9コア分でした。これは今回の測定条件での値です。

## 条件と計測負荷

同一の空/お邪魔4行盤面、公開next 12個、hold/speculation有効、batch=128、深さ32、ノード上限3200万。1条件3秒×3回、1/4ワーカーで合計12実行です。開発seedは42001〜42003。死亡・上限到達はなく、他のビルドやベンチを同時には実行していません。これは直前の速度比較と同じ形式の探索ベンチであり、公開next 6個で手を確定し続けるUltra全体のプロファイルではありません。

固定128バッチの通常版/計測版をAB/BAで3ペア比較し、ノード数・生成数など全探索統計、選択手、計画が全件一致しました。時間比（計測版÷通常版）の中央値は次の通りでした。

- 1ワーカー: 1.013倍（範囲 0.984〜1.047倍）。
- 4ワーカー: 1.015倍（範囲 1.004〜1.054倍）。

計測による増加は中央値で約1〜2%で、個別実行の揺れもあります。CPU clock取得単体は約0.1µs/回でした。1ワーカーでは測定した項目がCPU時間の約99.7%、各条件の工程別実時間の合計が約99.8%以上を説明しています。

計測は `profile-search` feature有効時だけ入り、通常ビルドではタイマーと集計フィールドが除かれます。

```sh
cargo build --release --offline --example profile_probe
# controlとして保存後、計測版を別名で保存
cargo build --release --offline --example profile_probe --features profile-search
# 各保存バイナリを指定して再測定
python3 tools/profile_search.py --control CONTROL --profile PROFILE --output NEW_OUTPUT
```

生データ、全コマンド、バイナリハッシュと通常版/計測版は `runs/experiments/search-profile-v1/` に保存しました。計測専用の整合性テストを含む51テストと、全機能のClippy（警告をエラー扱い）が成功しています。
